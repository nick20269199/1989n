## 二、五大专家设计

每个专家 = 独立进程，读共享输入文件，写独立输出文件。
依赖 external API（DeepSeek / Qwen），不是本地模型，所以 CPU 不是瓶颈。

### 专家1：技术面专家（DeepSeek）

| 项目 | 内容 |
|------|------|
| 模型 | DeepSeek Chat |
| 输入 | 股票K线 + R7信号 + 技术指标 |
| 输出 | `expert1_tech/{symbol}.json` |
| 回答 | 量价关系、支撑阻力、均线系统、形态识别 |
| 边界 | 不回答基本面，不回答消息面，越界 = Grader 扣分 |

### 专家2：资金面专家（DeepSeek）

| 项目 | 内容 |
|------|------|
| 模型 | DeepSeek Chat |
| 输入 | 资金流向 + 大单分布 + R7明细 |
| 输出 | `expert2_money/{symbol}.json` |
| 回答 | 主力动向、超大单异动、筹码分布 |
| 边界 | 不回答技术形态，不回答新闻 |

### 专家3：题材情绪专家（Qwen）

| 项目 | 内容 |
|------|------|
| 模型 | Qwen Plus |
| 输入 | 板块涨跌 + 涨跌比 + 涨停跌停 + CLS新闻 |
| 输出 | `expert3_sentiment/{symbol}.json` |
| 回答 | 板块轮动、市场情绪、新闻影响映射 |
| 边界 | 不回答个股技术面 |

### 专家4：宏观 / 大V交叉专家（Qwen）

| 项目 | 内容 |
|------|------|
| 模型 | Qwen Plus |
| 输入 | 大V雷达最新转录 + 宏观数据（美股/指数） |
| 输出 | `expert4_macro/{symbol}.json` |
| 回答 | 大V观点交叉验证、宏观环境、三V框架 |
| 边界 | 不回答具体技术点位 |

### 专家5：风控 / 对抗专家（DeepSeek）

| 项目 | 内容 |
|------|------|
| 模型 | DeepSeek Chat |
| 输入 | 其他4专家输出汇总 + portfolio + 止损规则 |
| 输出 | `expert5_risk/{symbol}.json` |
| 回答 | "如果他们都错了会怎样？""最坏情况是什么？" |
| 边界 | 这是 adversarial review 内置版本 |

### 并行可行性

```
DeepSeek: 6通道 → 专家1/2/5 同时跑3个，还剩3通道
Qwen: 3密钥 → 专家3/4 同时跑2个，还剩1密钥

→ 5个专家可以同时并行启动
→ 总API调用时间 ≈ 最慢的一个专家（通常20-30秒）
→ 全部跑完 < 1分钟（纯并行）
```

## 三、Grader 设计

独立进程，Qwen（research 通道），独立上下文窗口。

### 输入

5个专家的独立输出文件 + 原始问题

### 五维门禁检查

```
1. 方向明确？—— 多/空/观望，不能模棱两可
2. 方式透明？—— 用了哪些数据源、哪些推理路径
3. 轨迹清晰？—— 入场区间、目标位、时间框架、关键价位
4. 边际明确？—— 什么条件下判断失效、置信度衰减条件
5. 逻辑完整？—— 因果链完整："因为A所以B，如果非B则A假"
```

### 输出

```
{
  "passed": true/false,
  "scores": {"direction": 0.9, "method": 0.8, ...},
  "failures": ["边际: 未说明失效条件"],
  "merged_decision": "最终综合判断"
}
```

没过门禁 → 不发出决策包，打回 Lead 重新路由。

### 和 Lead 的关系

Grader 不阅读 Lead 的原始指令，只读专家的输出。
这保证：Grader 的评估不受到 Lead 的预设影响（U1 元层次分离的体现）。

## 四、Lead Orchestrator 设计

增强 `daily_task.py`，新增调度职责：

### 工作流

```
收到任务（定时/cli/手动）
  │
  1. 读配置：哪几个专家参与（默认全部5个）
  2. 准备共享输入：从 market_pool / stock.db 拉数据
  3. 并行启动5个专家（ThreadPoolExecutor max_workers=5）
  4. 等待全部完成或超时（默认60秒）
  5. 汇总专家输出 → 送 Grader
  6. Grader 返回 → 通过则输出决策包
  7. 未通过 → 记录失败原因 → 可选重跑失败专家
  8. 记录完整日志到 SQLite（谁、何时、输出了什么、门禁状态）
```

### 执行模式

- **全模式**（盘前/盘后）：5专家全跑 + Grader
- **快速模式**（盘中）：仅专家1+2（技术面+资金面）+ Grader
- **风控模式**（止损触发）：专家5（风控）单独跑，不经过 Grader（硬约束）

### 当前已有基础

`daily_task.py` 已经 78KB，有 8 种模式：
- `morning_enhanced`、`closing_review`、`intraday_analysis`
- `hot_stocks`、`evening`、`overnight`
- `tech_scan`、`position_check`

增强方式：在这些模式底层接入专家管线，不破坏现有接口。

## 五、Dreamer 设计

不是实时进程，是定时触发的批处理。独立于主流水线运行。

### 触发

- 每天收盘后（17:00+）
- 每周深度（周六，与 weekly-audit 结合）

### 工作内容

```
1. 读 SQLite decision_log: 过去N天的决策记录
2. 对每条决策，对比：预测 vs 实际走势
3. 模式识别：
   - 哪个专家经常错？（技术面在趋势市错了3次→下调权重）
   - 哪个市场状态下表现差？（震荡市集体命中率低→降频信号）
   - 哪个信号反复失效？（R7在XX股票失效→加边界条件）
4. 输出：
   - 专家权重调整建议（写入 config）
   - 规则修正建议（写入 trading_discipline）
   - 新模式发现（以前没见过的有效模式）
5. 所有输出需人工确认后才生效（"保护带"自动，"硬核"需确认）
```

### 和 weekly-audit 的关系

Dreamer 是数据驱动（读决策日志 vs 实际走势，统计模式匹配）
weekly-audit 是认知驱动（读压缩摘要，模式识别，ego death检查）
**两者互为补充，不是替代。** Dreamer 找"什么错了"，weekly-audit 找"为什么错了"。

## 六、进程模型

```
Lead Orchestrator（主进程）
  │
  ├── 启动 5 个 Worker 子进程（并行）
  │     ├── 专家1 (Thread 1) → deepseek API → 写 expert1_tech/*.json
  │     ├── 专家2 (Thread 2) → deepseek API → 写 expert2_money/*.json
  │     ├── 专家3 (Thread 3) → qwen API → 写 expert3_sentiment/*.json
  │     ├── 专家4 (Thread 4) → qwen API → 写 expert4_macro/*.json
  │     └── 专家5 (Thread 5) → deepseek API → 写 expert5_risk/*.json
  │
  ├── wait 全部完成
  │
  ├── 启动 Grader（单进程）→ 读5个输出 → 评估 → 写结果
  │
  └── 输出决策包 + 写日志

Dreamer（独立进程，定时触发，无实时依赖）
```

### 关键设计决策

1. **子进程写文件交互，不做 IPC 实时通信**：解耦、可审计、可重放。每个人都可以单独重跑。
2. **Thread pool，不用 Process pool**：API 调用是 IO 密集型，不是 CPU 密集型。线程池就够了，5 个线程不争抢。
3. **独立超时控制**：每个专家有单独的超时（默认 60 秒），一个挂了不影响其他人。
4. **中间文件自动清理**：超过 7 天的中间文件自动删除。
