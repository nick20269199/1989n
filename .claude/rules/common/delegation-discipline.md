## 执行铁律（20条，优先级降序）

1. **全揽=事故** — 接到任何任务，第一反应是"这活分给谁？"不是"怎么干"。可拆任务不拆=零容忍。

2. **有专用 Agent/Skill 必须用** — code-reviewer / stock-deep / planner 等可用且匹配时，不准自己硬做。绕过了=态度问题。

3. **可拆任务必须并行拆** — 能并行给 Agent 的必须并发执行，不准自己串行一件件做完。

4. **改代码前先 Read 文件** — 不准用记忆替代文件内容。工具强制了，但心态不能退。

5. **改完后必须验证三步** — exit code=0 + 输出非空 + 内容合理。少一步=没完成。

6. **报错先读 last_error.txt** — 不接受转述，不凭记忆猜错误是什么。

7. **不读规则就跳过=零容忍** — 没有"这个我知道"这回事。规则文件必须读。

8. **知识路由关键词必加载 Skill** — 出现关键词先 Skill 工具加载，不确定默认加载。

9. **跨部门工作必须通知对应部门** — publish_status + enqueue_task，做完即发。

10. **接到部门 cue 当场响应** — Q到谁谁就做，不等用户传话，三步完成。

11. **失败必须记录** — 问题/根因/修复/防复发，写 memory/feedback/。

12. **跨会话先读记忆** — 修旧问题前先读 interaction-patterns.md + memory/ + last_error.txt，不重复踩坑。

13. **模糊指令先确认再动手** — "你说的是 A 还是 B？"确认后再做。理解偏差=全方向白做。

14. **分析必须有因果+交叉+前瞻** — 博士生大脑不做白开水输出。为什么涨/跌（因果）+ 多因子交叉 + 前瞻判断。

15. **架构变更走 4 步模式** — P0 全盘查 → P1 分层实施 → P2 零残留验证 → P3 运行时测试。一关不过不进下一关。

16. **修改返回类型必须全链路更新** — grep 所有调用点 + 追入下游函数签名。三步检查法：签名→调用方→消费者。

17. **交付前强制验证** — 正常模式 → 边界条件（空输入/None/缺失文件） → 输出内容交叉校验。缺一不可。

18. **检测系统必须有配套执行层** — 只报警不自动修 = 没做。告警钩子必须挂执行脚本。

19. **cron trigger + 采集脚本同步交付** — 定时任务和采集脚本是一个整体单元，不设空闹钟。

20. **不确定该分给谁时，先问协调 Agent 而不是自己猜** — 兜底路由用 task-router.py，阻塞直接执行。

## 零容忍（触犯即停止→记录→修复→重做）

| 零容忍项 | 表现 |
|----------|------|
| 可拆任务不拆自己全包 | 5 个子任务可并行派 Agent，全部自己做 |
| 有专用 Agent/Skill 不用 | code-reviewer / stock-deep 可用且匹配，自己硬写 |
| 不验证说完成了 | 修完不跑 exit code 就说"修好了" |
| 不读规则就跳过 | "这个我知道" → 规则里写的是相反的 |
| 知识路由不加载 | 出现关键词不加载对应 Skill 就推理 |
| 交易数据出错 | 持仓/盈亏/方向 出错 → 全链条分析作废 |

## 会话开始自检

1. 工作目录是 D:/1989n？→ 不是先 cd
2. 读最新 3 条 feedback memory → 看用户最近纠正了什么
3. 读 last_error.txt → 有待修复的错误？
4. 读 interaction-patterns.md [待调整项]
5. 过一遍上面 20 条铁律
6. 确认当前部门 → 读 ops-standards.md 对应章节
