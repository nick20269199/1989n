# 流程铁律

## 0. 零号标准 — 100%执行铁律（P0 · 覆盖所有部门所有任务）

**每次执行的标准只有一个：100%正确执行，零误差、零失误、零跳过、零懈怠。**

### 定义

| 维度 | 含义 |
|------|------|
| 零误差 | 数据/代码/输出，不允许出现可避免的错误 |
| 零失误 | 每个操作步骤完全按照要求执行，不遗漏 |
| 零跳过 | 没有"这次可以简化"的判断，所有规则/指令都是必须执行的 |
| 零懈怠 | 态度上不降级，不因"赶时间""差不多"放松标准 |
| 零容忍 | 违反上述任一条 = 态度问题，不是能力问题 |

### 适用范围

- 此标准覆盖：前厅部/情报部/工程部/研发部/读书郎，全部部门
- 覆盖所有任务类型：代码修改/数据分析/策略判断/知识管理/日常运维
- 用户指令 = 必须执行，不经过"我觉得重不重要"这个过滤器

### 违反处理

违反零号标准 → 立即停止当前任务 → 记录违反事实 → 修正后从断点处重新执行 → 事后将违反记录写入 memory/feedback/

### 与其他规则的关系

此标准是基底规则，优先于后面所有具体规则。具体规则告诉你"做什么"，零号标准决定"怎么做"——100%执行，不打折。

## 1. 处理旧问题先查记忆（P0）

遇到以下任务时，必须先查记忆文件再动手：
- 修复/排查/诊断类任务
- 重现之前修过的 bug
- 涉及数据源/数据路径的配置任务

**操作步骤：**
1. 读 `interaction-patterns.md` 看[待调整项]
2. 读 `memory/` 下相关主题的反馈记录
3. 读 `last_error.txt` 确认最新错误上下文
4. 如果记忆中有匹配的失败记录 → 直接参照已知根因+修复方案，不从头查
5. 修复完成后 → 把本次执行结果也写入记忆

## 2. 失败必须记录（P0）

每次执行失败（包括脚本报错、决策错误、规则违反）必须记录：

**记录内容：**
- 问题：出了什么错
- 根因：为什么会错（知识盲区/惯性输出/路径遗忘/验证缺失）
- 修复：怎么修好的
- 防复发：下次怎么避免

**记录落点：** `memory/feedback/failure-YYYYMMDD-短描述.md`
**MEMORY.md 索引：** 追加一行到对应日期段

**禁止：** 只记成功不记失败，口头说"下次注意"不留记录。

## 3. 交付前强制验证（P0）

每次代码修改/新建脚本后，交付前必须完成以下验证，任一步不通过就回到修改，不跳过：

**操作步骤：**
1. 跑一次正常模式，确认 exit code = 0
2. 检查输出文件已生成且非空（stat 确认 size > 0）
3. 跑一次边界条件（空输入/None/异常数据/缺失文件）
4. 读输出内容确认格式正确、数值合理
5. 如果改的是 bug 修复 → 确认 root cause 确实被解决了再报告

**验证标准：**
- exit code = 0（非 0 = 立即排查，不继续）
- 输出文件存在且 size > 0
- 边界条件不崩溃（预期报错 ≠ 崩溃）
- 输出内容与已知正确数据交叉校验

**禁止：** 代码写完就说"完成了"、"应该能用了"，不跑实际验证。

## 4. 架构变更4步模式（P0）

涉及**重命名/部门重组/路径迁移/架构重构**等跨文件变更时，必须按以下4步模式执行。一关不过不进下一关。

**模式价值**: 不是保证最优，是保证可靠。每一步都基于上一步的完整产出。

### P0 — 全资产盘查
在**动手改任何代码之前**，在全仓库范围内（包括 `.claude/`、`stock_data/`、`.md` 文件）grep 所有旧名称/旧路径/旧字符串。

```
grep -r "旧名称" --include="*.py" --include="*.json" --include="*.md" --include="*.bat" --include="*.{yml,yaml,cfg,ini}" .
```

产出：完整的影响范围清单，每个命中点必须分类：
- **必须改** — 逻辑引用/路径引用/配置引用
- **可选改** — 历史注释（说明"原XX职能"的保留，不触发报警）
- **不改** — 历史记录/备份文件

**禁止**: 凭直觉判断"大概改这些文件"，不列清单就动手。

### P1 — 分层实施
按以下分层顺序修改，每层改完立即验证（grep 确认该层零残留）：

```
数据层（JSON/协议文件/配置文件）
  → 逻辑层（py 函数/类/变量/import）
  → 表现层（消息文案/注释/测试数据）
  → 配置层（.claude/settings.json / 定时任务 / hooks）
```

**禁止**: 跨层跳跃——改完数据层还没验证就跳到逻辑层。

### P2 — 全仓库验证
重新执行 P0 的 grep。每一个残留命中点必须手动确认：
- 确认是 False Positive → 注明原因放过
- 确认是遗漏 → 立即修复
- 无法确认 → 不放过

**标准**: 零容忍。除非能在注释+commit message 中说明为什么这个残留是必要的，否则必须改。

### P3 — 运行时验证
1. 每个被改动的模块独立跑一次（exit code = 0）
2. 涉及路由/映射的变更，跑一次集成测试（pytest）
3. 涉及运行时配置的变更，跑一次该模块的 CLI 入口
4. 边界条件：空文件/None/异常输入/缺失文件

### 模式进化机制

每次通过此模式发现遗漏（某步本该抓住但没抓住）→ 改进该步的检查项：
- P0 漏了某类文件 → 把该类文件加入扫描范围
- P1 某层改完有残留 → 该层增加一个验证节点
- P2 有残留没被 grep 抓到 → 检查 grep 模式是否需要补充
- P3 测试通过了但运行时依然有问题 → 补充测试 case

> 对应原则: 嵌套分层律(分层实施) × 乘法质量律(每步独立验证) × 实时校准律(模式进化) × 涌现简约律(4步叠加产生可靠性)
